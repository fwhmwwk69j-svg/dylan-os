# V1.6 Phase 2A — local-only atomic operations

Three additive migrations follow the original immutable V1.5.2 migrations:

1. `202610090004_collection_ordering.sql`: internal positions on ten record tables; deterministic backfill; ordered exports and writes.
2. `202610090005_operation_receipts.sql`: default-deny account-private operation/deletion receipts, UUIDv7 validation, status RPC and operator-only bounded cleanup.
3. `202610090006_atomic_operations.sql`: atomic operations, ordering, linked deletion, scoped Undo and a backward-compatible legacy command wrapper.

**Deployment is not authorized.** These files have been applied only to the disposable local test database. Do not run `supabase db push` from this checkout against hosted staging. No application cloud adapter, authentication UI, real-account access, import/clear/migration workflow, production connection or Phase 2B functionality is enabled. App continues using the existing local repository and keys.

## API contract

`dylan_execute_operation(request jsonb)` accepts:

```json
{
  "version": 1,
  "operationId": "UUIDv7",
  "expectedRevision": 12,
  "operation": {
    "action": "batch",
    "mutations": [
      {
        "action": "upsert",
        "collection": "tasks",
        "record": { "id": "stable-id", "name": "..." },
        "expectedRecordRevision": 0
      }
    ]
  }
}
```

This abbreviated record illustrates the envelope; actual records require the existing complete domain fields. `src/persistence/operationContracts.ts` defines the wire request/receipt/result types. It performs no network calls. The application-level Phase 1 identity/revision envelope is not sent directly: ownership is always derived by the server, and wire expectedRevision is the numeric workspace revision. Goals are nested in `operation.goals`, matching the established RPC conventions.

Supported operations: record upsert/delete, record-only batch, preferences, goals, reorder, Undo. Import, clear and snapshot restore are not new operation actions. Existing `dylan_read()`, `dylan_export()` and `dylan_command(command jsonb)` signatures and response shapes remain intact. Legacy commands retain existing validation, CAS and snapshots; they do not gain idempotent retries or scoped Undo receipts.

Every call checks the existing staging allowlist and live session before receipt access. Anonymous/direct browser access to the two receipt tables is denied: forced RLS, no browser table grants, no permissive policies. Authenticated callers use the RPCs, whose security-definer functions have fixed `pg_catalog` search paths and server-derived ownership. Storage policy and staging eligibility remain unchanged.

## Atomic execution and revisions

The workspace row is the shared transaction lock for legacy and new commands. New requests validate account-scoped receipts before stale-revision checks, then validate the workspace revision and every explicitly targeted record against the pre-operation state. Inserts require record revision zero; deletion of a missing record is a conflict. The maximum safe integer cannot be incremented by either entrypoint.

Batches allow 1–100 explicit mutations and no nested batches or repeated targets. Requests remain capped at 256 KiB, individual records at 128 KiB and reconstructed workspaces at 5 MiB. Course creates/edits precede other upserts; deletions follow. Input ordinality breaks ties, preserving append order within collections. A single snapshot precedes the entire operation; all touched records get the new revision and the workspace advances once. Position-only changes advance the workspace, not content revisions.

Failure, including a final FK/uniqueness/size violation, rolls back all records, positions, workspace/record revisions, snapshots, receipts and Undo consumption. Account-scoped composite FKs remain active. Arbitrary unique-value swaps and overlapping course-cascade/explicit-child mutations are unsupported and rejected, rather than partially applied.

## Ordering

Each record table has a nonnegative bigint position and a deferred unique `(user_id,position)` constraint. The populated upgrade backfills the previously exported ID order without changing content, IDs or existing revisions. Historical order that was never stored cannot be recovered.

Edits preserve position; inserts append; deletes normalize surviving positions. `reorder` requires a complete array of the caller's current collection IDs, with no duplicates, omissions or foreign IDs. Legacy snapshot restore writes records in the payload's array order. Portable schema remains 6: positions are internal metadata, never added to exported record fields. If a portable unknown field is itself named `position`, it remains inert extension data and does not control internal ordering.

## Linked deletion and Undo

New course deletions require `expectedLinkedRevisions`, an exact map of all current linked school-work IDs/revisions, including `{}` for no children. The server enumerates and validates the actual inventory. Standalone delete captures records, unknown fields, optional-field presence and positions in an account-owned deletion receipt. Course receipt payloads include every linked assignment/exam. Generic batches do not provide Undo or silently omit cascaded records.

Undo accepts a deletion ID, expected workspace revision and a new UUIDv7 operation ID. It restores only captured records, parents before children, assigns new content revisions, and consumes the deletion receipt atomically. The server checks a 30-second deadline after acquiring the workspace lock; the client cannot extend it. Unrelated edits survive. Reused IDs, missing parents, unique-date/week conflicts, expired/consumed/foreign receipts fail without partial restoration.

Saved positions are reinserted in ascending order and clamped to current length; survivors retain their relative order. Concurrent reorders/insertions/deletions may mean the result differs from the historical full collection, intentionally preserving intervening work. Scoped Undo is independent of five-snapshot rotation. An identical successful Undo request can replay after the window because replay does not restore a second time. A new request against the consumed receipt fails.

## Idempotency and ambiguous outcomes

Receipts use `(user_id,operation_id)` keys and a server SHA-256 fingerprint of the JSONB request representation, including expected revision, operation and array order. Object-key order is canonicalized by JSONB. Clients must retry the same request; this is not general semantic equivalence (for example numeric lexical representations can differ). Reusing a key with a changed payload returns `PT409`/HTTP 409.

Operation IDs must be RFC 9562 UUIDv7. Their embedded millisecond timestamps permit a 24-hour new-operation admission window and at most five minutes of future clock skew. Matching committed receipts are checked first. Receipts remain for seven days; after cleanup, the embedded old timestamp prevents re-execution. Generating a different ID for an unresolved request is unsafe. UUIDv7 IDs/fingerprints are identifiers, not authentication credentials.

Response shape: `{ receipt, workspace, replayed }`. The compact receipt contains committedRevision, operationId, kind, deletionId (nullable) and committedAt. Workspace is a fresh authorized read: on replay it can have a higher revision than the original receipt. No historical full-workspace result is stored per request.

`dylan_operation_status(operation_id uuid)` returns committed plus receipt, not-found, or expired for the caller only. Not-found alone is not proof that an in-flight request cannot still commit; the client must reconcile or retry the identical key. A failed operation leaves no success receipt. Expired status without a retained receipt cannot prove whether a long-ago operation committed. Later client integration must label lost responses as outcome unknown, not “nothing changed.”

## Retention and operational disable

`dylan_private.cleanup_operation_receipts()` is trusted-operator-only and invoker-authorized. Each invocation removes at most 1000 operation receipts older than seven days and at most 1000 deletion payloads whose Undo deadline passed more than five minutes ago. Repeat bounded invocations as needed. No hosted scheduled job is installed. Payloads may remain longer without maintenance, but expired IDs still cannot execute and expired Undo still fails. Maintenance scheduling/monitoring needs separate deployment approval before hosted use.

`supabase/rollback/disable_cloud.sql` now disables the account allowlist and revokes both new RPCs as well as the legacy RPCs and actor helper. It preserves tables, receipts, ordering, snapshots and storage protection. Conditional revocation also supports the original three-migration schema, where the new RPCs do not exist. No hosted execution is authorized by this release. Re-enabling remains explicit after diagnosis and testing.

## Local validation and limits

Use the existing disposable containers, never a personal database:

```sh
./scripts/db-local.sh start
npm run test:db
./scripts/local-api.sh start
npm run test:api
./scripts/local-api.sh stop
./scripts/db-local.sh stop
npm test
npm run build
```

Stop PostgREST before rerunning `test:db`, which resets only the guarded local disposable database. SQL tests cover both a populated three-to-six-migration upgrade and the resulting full schema. HTTP tests use actual PostgREST JWT verification and actual RLS; identities/session rows are synthetic fixtures, not Supabase Auth-issued identities. New hosted behavior has not been verified. Phase 2A.1 prepares an expanded 24-test hosted suite, retaining the original 13 checks. It has not been executed against hosted staging. See [test preparation](staging-setup.md#v16-phase-2a1--hosted-test-preparation).

Existing limitations remain outside 2A: root-extension reconstruction during full snapshot restore, bulk import/migration, protected migration backups, authentication refresh/UI, production eligibility and offline drafts. PostgreSQL still normalizes timestamp spellings (for example `Z` to `+00:00`) while preserving the instant; future migration comparison must account for that or explicitly preserve lexical forms. No local data is rewritten. Performance at large workspace sizes and hosted retention scheduling require a later checkpoint. Phase 2B and hosted deployment both require approval.
