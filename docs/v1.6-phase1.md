# V1.6 Phase 1: contracts and compatibility

Phase 1 defines contracts only. App still constructs LocalWorkspaceRepository. No authentication, cloud adapter, migration UI, data transmission, hosted changes or database migrations are enabled. Existing storage keys and raw-string revision behavior are unchanged. Cloud operation types describe future intentions, not supported RPC actions.

## Identity, revisions and capabilities

`domain/workspace.ts` identifies local workspaces by namespace and cloud workspaces by environment/project/account. Its JSON tuple key prevents ambiguous delimiter joins. Identity is routing context, never authorization; verified server sessions must establish ownership. Existing WorkspaceOwner remains unchanged for compatibility; future cloud code uses the richer WorkspaceIdentity, not an account ID alone.

`persistence/contracts.ts` defines exact-byte local revisions, nonnegative safe-integer server revisions and record revisions, explicit capabilities, operation envelopes, and typed errors. The existing repository interface/controller remain operationally unchanged. LocalWorkspaceRepository exposes additive identity/capability metadata. It does not claim operation execution or idempotent request support. Future OperationRepository is deliberately separate from the legacy whole-workspace-save interface; bridging those interfaces requires Phase 2+ design and implementation, not a loop of individually committed cloud commands.

Operation envelopes bind workspace, expected revision and operation ID. Imported ownership, revisions, permissions or entitlements remain inert portable extension fields; they cannot authorize commands. Server code must derive ownership and revisions independently. Confirmation strings and imported payloads require server validation even when TypeScript types are correct.

Error codes distinguish validation, loading, conflicts, connectivity, forbidden resources, expiry, stale accounts, quota, unavailability and unknown commit outcomes. An unknown outcome requires operation reconciliation before retry. These contracts do not change current local error messages.

`auth/contracts.ts` defines disabled/signed-out/authenticating/active/refreshing/expired states, account generation guards and a lifecycle interface. Observable state contains no credentials. Guards compare environment, project, user and generation; expired/disabled states reject pending responses. Expiry transition/refresh/sign-in and request cancellation have no implementation in this phase. No tokens are obtained or stored.

## Every current local operation: cloud equivalent or blocker

All record writes need server-derived ownership, workspace CAS and record CAS. Existing staging commands are synthetic-only.

| Local operation                                            | Existing staging equivalent                       | Blocker before UI cloud integration                                                    |
| ---------------------------------------------------------- | ------------------------------------------------- | -------------------------------------------------------------------------------------- |
| Load workspace; Today/planner/review/chart/Assistant reads | `dylan_read`                                      | Adapter/session lifecycle and loading/error states                                     |
| Subscribe/reload on another tab's changes                  | Local storage events only                         | Account-scoped cross-tab notifications and remote freshness polling                    |
| Add/edit task; complete/reopen task                        | Task upsert                                       | Operation adapter; preserve field extensions and order                                 |
| Add/edit course; grades and course notes                   | Course upsert                                     | Same; preserve linked work                                                             |

| Add/edit weight or nutrition/steps by date                 | Weight/nutrition upsert                           | Date uniqueness, preserved stable IDs, no partial multi-record writes                  |
| Add/edit workout; complete/reopen workout                  | Workout upsert                                    | Same; historical date rules must agree                                                 |
| Add/edit habit; completion count/history; schedule edits   | Habit upsert with owned nested history            | Preserve unknown nested fields and effective-date semantics                            |
| Add/edit important date                                    | Date upsert                                       | Preserve order and stable IDs                                                          |
| Save recurring commitment and exceptions; delete series    | Commitment upsert/delete                          | Floating-date semantics remain; no stored duplicate occurrences                        |

| Import backup/replace workspace                            | No equivalent                                     | Validated atomic import, preview/consent, CAS, idempotency, root extensions            |
| Automatic snapshots/list/preview/download                  | Account snapshots exist                           | Repository shape differs; account-specific metadata; retention policy                  |
| Confirmed restore                                          | `restore` command                                 | Root extensions and ordering not fully restored today; confirmation/account binding    |
| Confirmed clear                                            | No equivalent                                     | Atomic clear with pre-clear recovery and CAS                                           |
| First edit of legacy local data                            | Exact original-byte snapshot already local        | Preserve local behavior; cloud normalization must never rewrite local source           |
| Theme preference                                           | Device-local key                                  | Keep device-local; no RPC required                                                     |
| Backup reminder dismissal/export download confirmation     | Device-local global keys                          | Scope cloud status by environment/account; never imply another workspace was backed up |
| Presence notices                                           | Global browser channel                            | Scope notifications without personal payloads                                          |
| Form validation/import preview/date projections            | Local pure functions                              | Server revalidation before writes; server dry-run upload needs consent                 |

Generic whole-workspace update can encompass several rows; `batch` is a proposed atomic contract, not an existing staging feature. Existing records, snapshots, unknown fields, optional values and original array order must survive import/export/restore. Finances and Library remain registered future modules without data collections or new pages.

## Fixtures and acceptance evidence

`testing/compatibilityFixtures.ts` creates fresh synthetic unversioned and schema 1–6 workspaces. Fixtures include deliberately unsorted IDs, academic links, absent optional fields, explicit nulls, nested unknown fields, duplicate habit names, date logs, exercise records, and schema-appropriate planner/reflection records. Habit history remains nested data. No fixture reads real browser storage.

Compatibility tests verify non-mutating load/normalization, idempotent IDs, collection equality/order, known IDs/links, unknown fields, omitted-versus-null values, normalized export/import and exact original snapshot bytes before edits/restores. Existing safety/cross-tab/application tests continue to cover corruption, quota, rotation, Undo and concurrent local saves. Fixtures are representative supported shapes, not a claim to possess historical user datasets or exhaustive fuzz coverage.

## Remaining gaps and next gate

Cloud bulk import/clear/batch/Undo, idempotency, order persistence, full root-extension restore, protected migration recovery, validation/size parity, session refresh and production eligibility remain unimplemented. The backend exports collections by ID, restricts IDs to 200 characters, commands to 256 KiB, preferences to 32 KiB and reconstructed workspaces to 5 MiB. These must be resolved through separately approved additive backend changes. No existing migration is changed here.

Phase 2 requires separate approval. No hosted tests are run for Phase 1; previous hosted results are independent reported checkpoint evidence, not proof of the future contracts.
