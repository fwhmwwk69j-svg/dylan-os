# Dylan OS cloud migration: approved staged architecture

Version **1.5.1 is local architecture preparation only**. There is no authentication, Supabase connection, upload, cloud cache, billing, external integration, or paid AI. This plan supersedes the Version 1.4 proposal to use one JSONB workspace as the primary cloud database and to deliver all cloud functionality in one Version 1.5 release.

## Product and architecture decisions

Keep React, TypeScript and Vite. Use a modular monolith with domain commands, portable validation, a replaceable repository, and independently scoped domain services within one application. PostgreSQL/Supabase remains appropriate for a future multi-user SaaS: relational ownership and constraints provide the foundation; JSONB holds preferences, extension fields and recovery documents, rather than replacing relationships and queryable records. Deployment and provider setup require a later approved milestone.

The six command centers are Home, Health, Finances, College, Life & Goals and Personal Library. `src/platform/modules.ts` registers all six and maps current routes to available functionality. Planned centers create no empty pages. The ten longer-term lifestyle features—calendar, goals, journal, notifications, food, documents, life simulator, integrations, privacy and relationships—should reuse the same ownership, scheduling and permission boundaries. Home aggregates data without owning duplicate copies.

Initial commercial launch is **18+**, focused on college students 18–24. Free/paid subscriptions and independent private accounts are future requirements. Customizing or hiding modules changes presentation, not permission. High school expansion needs a separate age, consent and safeguarding review before supporting minors; no age gate or monetization is activated locally.

## What Version 1.5.1 establishes

- `src/application/commands.ts` holds pure form and destructive commands; `workspaceController.ts` coordinates writes, recovery and Undo. React uses `useWorkspace.ts` rather than accessing storage in `App.tsx`.
- `src/persistence/repository.ts` defines asynchronous load, expected-revision save, snapshot listing, original-byte recovery and change subscription. `localRepository.ts` retains existing storage keys, validation, Web Locks and exact-JSON compare-and-swap. Preferences/export confirmation remain separate in `preferences.ts`.
- Schema **6** adds stable IDs to weights, nutrition/steps entries, habits and important dates. Existing IDs and references remain unchanged. New records use UUIDs; legacy missing IDs use deterministic scoped text identities, with collision suffixes. Habit completion identity is the habit ID/calendar-date pair, not a newly generated record per load.
- Loading, import preview and export normalization do not write storage. The first successful modification of legacy storage must snapshot its exact original bytes before saving schema 6. Failure to create that snapshot blocks the modification. Five-snapshot rotation, explicit restore/import confirmation and Undo remain.
- Schemas 1–5 and unversioned legacy JSON remain importable, including older snapshots. Schema 6 requires the added IDs and rejects duplicates/corruption. Validators preserve unknown root and record fields. Legacy duplicate names/dates remain records; no silent deduplication occurs. Existing dated-log validation still enforces one weight/nutrition log per date.
- `src/domain/contracts.ts` separates owner context from portable data, documents mandatory assignment/course links and optional selected-task references, and defines future revision/source metadata. Historical timestamps remain unknown rather than fabricated.
- `src/platform/access.ts` defines inactive AI scope/field allowlists and entitlement/usage contracts. They do not authenticate anyone or call a model. Existing assistant remains a local preview; any future external provider must use an authenticated scoped service rather than sending its full-state interface directly.

Repository ownership in local mode identifies a browser workspace namespace; **it is not user authentication**. Account ownership must later come from a verified server session. An unknown `owner`, `entitlements` or `permissions` field in an imported file is retained as inert data and must never become authorization context.

## Scheduling and relationships

Calendar dates are `YYYY-MM-DD` values, not UTC instants. Existing UI follows the device's local date. Day arithmetic and weekdays use calendar arithmetic and remain stable across daylight-saving transitions. `todayInZone` and an injected clock define explicit IANA-zone behavior for future account settings without changing current dates.

Current recurring commitments retain floating local wall times, inclusive start/end dates and exception dates. Occurrences are derived using `(series ID, calendar date)` and are never stored as duplicate rows. Tasks/assignment due dates remain flexible deadlines; a due date does not silently become a fixed calendar interval. Future fixed events store offset instants plus an IANA zone; half-open intervals permit back-to-back events. Ambiguous/nonexistent DST wall times need an explicit conversion policy before introducing zoned event entry. Never retroactively convert historical local dates into guessed UTC instants.

Academic records belong to College, fitness logs/goals to Health, tasks/habits/commitments/reflections/important dates to Life & Goals; Home only composes them. See [the proposed relational model](relational-schema.md). Future cross-module links carry an owner and typed record reference. Foreign keys must include owner scope. Optional dangling task priorities can be filtered for display without deleting imported unknown fields. Shared calendar membership is a narrowly scoped exception to private ownership, not workspace-wide access.

## Future multi-user security and transactions

Derive user ID from verified Supabase Auth, never from a request body or export. Enable RLS on every private table and file bucket; anonymous access fails. Test two users through direct REST/database/storage requests, not just UI routes. User B cannot read/write/list/export/restore A's rows, snapshots or documents. Composite owner/record foreign keys prevent cross-user links. Privileged server paths must independently enforce ownership because service roles bypass RLS. Secrets stay server-side.

Store academic, health and financial records in private tables with narrow field access, encryption in transit/at rest and documented retention. Collect only necessary data. Never put personal payloads, tokens, raw documents or AI context into telemetry. Provider encryption is not a claim of end-to-end encryption. Financial features initially track records; movement of money and credential collection need separate designs and approval.

Use a per-workspace server revision with transactional compare-and-swap. An authenticated command transaction locks the workspace revision, rejects a stale expected revision, backs up the prior state when required, validates domain relationships, applies normalized row changes and increments revision atomically. Import/restore/clear/course cascade use the same unit of work. Return conflict without partial writes or snapshots. A document snapshot is the portable reconstruction of normalized rows; it is not the primary mutable database. Large-scale snapshot retention/size policy must be set before production.

Keep drafts on conflicts and session expiry. Web Locks only coordinate one browser origin. Cloud writes require server revision checks. Begin with online cloud writes; offline edits remain drafts and are not automatically queued. Logout/account switching hides and clears active account caches under a defined shared-device policy. Never automatically reveal the original local workspace on logout.

## AI, integrations, subscriptions and deletion

Future AI context has independent owner checks, user-granted scopes, bounded queries/time ranges, field allowlists, provenance and deterministic calculations. Defaults deny access; finance/journal/documents require granular explicit consent. Recheck consent at request time, not only at setup. Treat notes/documents as untrusted content. Cross-module answers combine only separately authorized scopes. Tool writes require a preview and confirmation plus the usual domain command/revision checks. Permission grants are not subscription entitlements.

Integration connections belong to accounts; credentials are encrypted server-side, never portable exports. Minimal OAuth scopes, revocation, idempotent external source IDs, replay-safe webhooks and explicit conflict ownership are required. Notifications respect account zone/preferences and consent. No integration is connected in 1.5.1.

Subscriptions use server-verified entitlements and idempotent webhook processing. A client flag/export cannot grant paid access. Usage reservations use request IDs and atomic reserve/settle/release. Keep personal export and account deletion available regardless of plan. Billing data should reference provider identifiers rather than card data; visibility settings do not enforce entitlements.

Account deletion requires reauthentication/strong confirmation, immediately disables access/jobs, revokes integrations, removes private rows/files and caches, handles calendar membership, and schedules backup expiry under a published retention policy. Define billing cancellation/refunds and minimal legally required retained records before launch. Restore must not resurrect a deleted account's data or credentials. Export portability and personal recovery are separate from provider disaster recovery.

**Do not begin 1.5.2 without approval.** Its scope excludes importing real personal data, activating production cloud mode, paid AI, billing, external integrations, sharing UI or a visual redesign. Use normalized tables for existing domains first, not speculative implementations of all future features.

Real-data migration in 1.5.3 must be explicit and reversible: verify a downloaded backup, preview source/destination, obtain upload approval, validate and transact, re-read and compare IDs/counts/history/goals/preferences/extensions, then switch adapters. If the destination already has data, require an explicit replacement choice and backup it first; automatic merge is out of scope. Failed/cancelled migration leaves original local data usable.

## Version 1.5.2 implementation status

Staging backend code now exists in `supabase/migrations`: typed owned domain tables, forced owner-read RLS, composite academic FKs, active-session/administrator-allowlist checks, transactional expected-revision commands and account-scoped snapshot restore. LocalStorage remains the only repository constructed by App. See [staging setup and verification](staging-setup.md) and [the server boundary](../backend/README.md). No hosted deployment or real-data upload has happened. Hosted security is unverified until the separate credentialed runner passes; local PostgreSQL/PostgREST tests are distinct evidence.
